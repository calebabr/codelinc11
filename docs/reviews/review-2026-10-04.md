# Review before a public demo (2026-10-04)

Scope: what was added since `review-2026-10-03.md` and is now on `main`: demo sandboxes and rate limits, notifications, profiles and family editing, Find Providers, Reports (and the assistant's reports scope), the quote reader changes, and the matching frontend. Read-only; no code was changed.

## Verdict: ready for a public demo? NO, not yet. Fix items 1 to 3 first (about half a day), then YES.

The money rule and the access rules hold up well: every dollar on the new pages comes from the engine or from stored values, golden numbers still pass, and one member cannot read another member's reports, notifications or provider estimates. The problems are about being on the open internet: the abuse controls can be bypassed with one header, sandbox ids can be guessed, and an in-memory upload store never empties. There is also one visible gap (the Reports "Explain this" panel drops the plain-language sentences).

## Must fix before the demo

1. **The per-IP limits can be bypassed with a forged header, so sandbox creation and the Anthropic key are not protected.**
   `backend/app/ratelimit.py:87-93` trusts the FIRST hop of `X-Forwarded-For` when `TRUST_PROXY=1`. The first hop is whatever the visitor sent: nginx (`infra/aws/nginx.conf`, `$proxy_add_x_forwarded_for`), CloudFront and (suspected, not verified) Netlify all append to an incoming header rather than replace it. Also `netlify.toml` sends traffic to `http://3-149-89-171.sslip.io:8000`, so the API is reachable directly and a script can set any `X-Forwarded-For` it likes.
   See it: call `POST /auth/demo-login` with `{"member_id":"m-jordan","sandbox":true}` repeatedly, changing `X-Forwarded-For` each time. The 10 a minute limit (`ratelimit.py:129-133`) never fires.
   Effects: (a) one script can create sandboxes until `DEMO_MAX_SANDBOXES` (300, `db/sandbox.py:162-176`) evicts every real visitor's family (they see a silent restart, or 404 errors, see item 9); (b) each sandbox has its own chat bucket (200 a day), so one person can burn the whole `CHAT_GLOBAL_DAILY_CAP` (3000 messages a day, `ratelimit.py:136-141`) and switch the assistant off for everyone; the cap does keep the spend bounded, which is good.
   Fix: take the LAST address added by your own proxy (or `X-Nf-Client-Connection-Ip` on Netlify, or the right-most-minus-N hop), never the first. Add a per-IP chat limit besides the per-household one. Close port 8000 to everything except the proxy if possible.

2. **Sandbox ids are only 6 hex characters and `demo-login` confirms whether one exists, so another visitor's family can be taken over by guessing.**
   `db/sandbox.py:22` (`SID_RE`) and `:186` (`secrets.token_hex(3)` = 24 bits), `routers/auth.py:32-39`: `POST /auth/demo-login` with `{"sandbox":true,"household_id":"hh-lincoln.<guess>","member_id":"m-jordan"}` returns a token for the primary account if the sandbox exists and 410 if not. Nothing limits that path (only creation is limited, `auth.py:44`). With up to 300 live sandboxes, about 1 guess in 56,000 hits one, so a loop finds a victim in minutes. `GET /auth/demo-accounts?household_id=` is the same oracle (`auth.py:23`). The attacker then reads and edits that family's profile (emails and phone numbers people typed, even though the form says "made-up"), reports and chat, and spends their chat budget.
   Fix: make the family id carry a real secret (at least 64 random bits, 16 hex or more) or require a separate secret that the browser keeps in `localStorage` with the family record; count failed `demo-login` and `demo-accounts` lookups per IP (see item 1 for the IP) and return the same error for "unknown" and "expired".

3. **`_ATTACHMENTS` grows without limit and is never cleaned.**
   `backend/app/routers/chat.py:58`, `:189-191`. Each upload keeps up to 5 MB in RAM forever (until restart), nothing removes it after use, on sandbox expiry or by age; the only limit is 5 uploads a minute per household, and households are cheap to create (item 1). A few hundred uploads exhaust a small EC2 instance and take the whole demo down. The request body is also read whole before the size check when no `Content-Length` is sent (`chat.py:184`; same pattern in `routers/reports.py:97`, 20 KB limit there but still buffered first).
   Fix: cap total bytes and count (evict oldest), expire entries after about 30 minutes, delete when the sandbox is deleted, and stop reading the body past the limit.

## Should fix

4. **Reports "Explain this" drops the plain-language text the server sends.**
   Server: `backend/app/reports.py:268-298` (`lines` = `{label, amount, plain}`) and `:301-321` (`steps` = `{key, label, amount, plain}`). Frontend: `frontend/src/lib/api/reports.ts:129-134` reads step text from `note` / `text` / `description` and line text from `text` / `description`, never `plain`. Result: the line-by-line list never appears (all lines map to null), steps show only a label, an amount and a bar, and the "Note on the document" (the remark, for example "Not covered: this plan covers 2 cleanings per plan year") is never shown. The test fixture (`ReportsPage.test.tsx:26-38`) invents a shape the server does not send, so the tests pass. What does show: `what_it_is`, the balance-billing note and "What to do next". Fix: read `plain` (and `amount` on lines), update the type and the fixture to the real shape, add one test built from a real `/explain` response.

5. **A long conversation with the assistant breaks with a raw validation message.**
   `backend/app/models.py:183` (`messages` max 20) against `frontend/src/features/assistant/useAssistant.ts:48-52, 90-101`, which sends the whole thread. After 10 question and answer pairs, the next send gets 422 and the chat shows "List should have at most 20 items after validation, not 21." (`planYear.ts:41` shows the first validation message verbatim). The thread is kept across pages, so a rehearsal that reuses the browser hits it. Fix: send only the last 12 to 16 turns (trim in `turnsOf`) and cap the input length (server limit is 4000 characters per message, no `maxLength` on the box).

6. **SQLite with many public visitors: no WAL, no busy timeout, no 500 handler.**
   `backend/app/db/core.py:36-52` (`connect`: default 5 s lock wait, no `journal_mode=WAL`). Every notification poll (every 60 s per open tab, `useNotifications.ts:51-57`) runs `sync_notifications`, which writes (`routers/notifications.py:58`), plus chat memory, visits and sandbox creation all write. Under a crowd, "database is locked" becomes a bare 500 ("The server returned an error (500)."). Fix: `PRAGMA journal_mode=WAL; PRAGMA busy_timeout=5000;` in `connect`, and make the list endpoint skip the sync when nothing changed (or sync at most once a minute per member).

7. **Shared template family is still open to the public and writable in places.**
   `routers/auth.py:40-55`: `demo-login` without `sandbox:true` signs anyone in as Abraham in the shared template household, with no rate limit. Profile, report and notification-setting writes are blocked there (`store._editable_target`), but visits (`routers/members.py:106-131`), usage, saved plans, saved comparisons, invites, chat memory and `/demo/reset` are not, and they share one chat bucket (`hh:hh-lincoln`). The UI does not offer it, the API does. Fix: refuse non-sandbox `demo-login` unless a setting such as `ALLOW_TEMPLATE_LOGIN=1` is on.

8. **Expired sandboxes (and the emails and phone numbers typed into them) stay in the database until someone else starts a demo.**
   `db/sandbox.py:162-184`: cleanup runs only inside `create`. `get()` hides an expired family but does not delete it. Contact details are never logged and never sent to the model (checked: `agent/context.py` and `tools.py` use none of email, phone, ZIP or notes), but they do sit in `benefits.db` and in any backup. Fix: run `cleanup` on startup and from a periodic task; say plainly on the contact form that nothing typed there should be real (the help text exists, `features/family/contact.ts:68`).

9. **Mid-session failures show wrong or raw messages.**
   Token lifetime is 12 h (`routers/session.py:56-60`) but a sandbox lives 24 h; after the token expires every call returns 401 "Your session is not valid. Please sign in again." and nothing signs the person in again (`SessionContext.tsx` only handles 410, lines 192 and 240). If a sandbox is evicted, member lookups return 404, and `frontend/src/lib/api/reports.ts:29` turns any 404 into "Reports are not available on the server yet." (same pattern in `lib/api/providers.ts:30`). Fix: on 401 or on a 404 for the active member, run the existing "start a new family" path; limit the "not available yet" wording to the route-missing case.

10. **Assistant answers are fully buffered, and the Netlify proxy gives up after about 26 s.**
    `backend/app/agent/loop.py:565-573` only emits the answer after the model and the number check finish (up to 5 steps, 60 s per call: `loop.py:30`, `providers.py:70`). Tool chips do stream, but a slow answer can still pass the proxy limit and the person gets "The server returned an error (504)." (suspected: Starlette sends response headers at once, so Netlify may only count idle time; not tested). Fix: send an SSE comment heartbeat every 10 s, lower the provider timeout to about 20 s, and rehearse the two demo questions through the real Netlify URL.

11. **Direct leg is plain HTTP.** `netlify.toml:30-34` forwards to `http://...:8000`. Tokens and any typed contact details cross the internet unencrypted between Netlify and the server. `docs/DEPLOYMENT.md` says port 8000 must be open to the world. Fix: terminate TLS in front of the API (CloudFront or a certificate on the host). Also note `infra/aws/dental-api.service:13` binds uvicorn to 127.0.0.1 (nginx on port 80), which does not match the port 8000 target in `netlify.toml`; confirm which setup is live.

12. **No upload or parse limits on the public quote reader.** `routers/treatment_plan.py:21` (`/treatment-plan/parse`) and `/estimate`, `/schedule` (capped at 10 items), `/savings-tips`, `/questions` need no sign-in; the quote parser is the only one with no rate limit at all. The parser is regex only and capped at 20,000 characters (no model, so no key spend). Fix: add `limit_compute` to the parse route.

13. **Disclaimer coverage is good but not on every notification and report line.** Pages for Reports, Providers, Costs and Plan My Year carry the sentence; provider cards carry it in each estimate note; notification bodies with amounts carry it. The "Test notification" and the quote-reader results rely on the page footer. Acceptable; checked only by reading.

## Nice to have

14. `routers/reports.py`: documents can be added repeatedly, so totals double count (a second EOB with the same claim number is added again; only claims are de-duplicated against EOBs, `engine/reports.py:93-99`). Limit is `MAX_REPORT_ITEMS` per person. Add a "already saved" check on `claim_number`.
15. Names are letters only, 24 characters (`households.py:75-87`), and go into the prompt (`loop.py:459`); a 24-letter name cannot carry a real injection. Remarks and descriptions from a pasted document (200 and 120 characters) do reach the model through `explain_report` and are labelled "data, not instructions" (`loop.py:118`); the person can only attack their own chat. Fine for a demo.
16. ZIP search accepts only the 51 demo ZIP codes; the error lists five (`providers.py:31`). A visitor who types their own ZIP sees an alert plus a pointless "Try again" button (`ProvidersPage.tsx:252-258`). Hide the retry button for 422 and show the sample ZIPs as chips.
17. `/style` and `/welcome` are still routed (`App.tsx:30, 44`) with hard-coded example numbers; labelled in item 13 of the last review, not fixed.
18. `JoinPage.tsx:54` uses `dangerouslySetInnerHTML` for the QR code; the SVG comes from the QR library and encodes the address as shapes, so no injection is visible. Keep it that way.
19. `backend/Dockerfile` runs as root and has no `HEALTHCHECK`; `python -m app.db` seeds only an empty or missing database (it will not wipe an existing one), and migrations 008 and 009 run on the first request through `get_store` (`routers/session.py:63-69`), not at startup, so the first visitor after a deploy pays the migration and any failure shows as a 500. Run `migrate` in the `CMD`.

## What I verified

- **Tests (run on this checkout):** backend `pytest -q`: all pass except two tests that were failing while another agent was editing `backend/app/db/core.py` (`test_profiles.py::test_migration_005_upgrades_an_older_database` and `test_sandboxes.py::test_no_hard_coded_family_names_in_app_logic`); I re-ran both files after that edit settled and they pass. `tests/test_engine.py` passes (golden numbers G1 to G6 and S2 = 2,300 / 1,405 / 895 untouched). Frontend: `npm run typecheck` clean; `npm run test` 240 of 241 passed, and the one failure (`App.test.tsx`, `/costs` route, a 22 s lazy-load timeout) passed 15 of 15 when run alone, so it was machine load (I was running pytest at the same time).
- **Not run:** `ruff` (not installed in this environment), the app in a browser, 375 px layouts, a real Anthropic call, Netlify or AWS (no network checks), `npm run build`.
- **Access control (read in `db/store.py` and routers):** every reports, notifications, outbox, providers-estimate, usage and chat path goes through `_target` (primary in own household, or self), so an adult cannot read another adult's or a child's reports or notifications; report and notification ids are always matched with the member id (`store.py:518-528, 580-587, 609-627`), so a member cannot reach another member's item by id; attachments are bound to viewer and member (`chat.py:137`). Managed members have no login and get 403 (the Reports page handles it, `ReportsPage.tsx:69-73`). The reports chat scope loads rows through the same check (`chat.py:145`).
- **Money:** no dollar or percentage is computed in the new frontend files (only pixel widths for bars, `ReportCard.tsx:31`); provider estimates come from `engine.estimate` (`providers.py:84-89`); report totals are added in `engine/reports.py` from stored cents and the sample documents add up (checked the out-of-network EOB: allowed 1,200, deductible 50, coinsurance 575, plan paid 575, balance billing 300, you owe 925, which matches G5); notification amounts come from `benefits_status`; `template_answer` and the report tools only format tool results; the number guard runs on the reports scope too (`loop.py:541`).
- **Prompts and HTML:** notes reject `<` and `>`, names are letters only, documents accept only the fixed template (anything else gives one fixed message and is never echoed or logged), React escapes everything else; contact details are never in the prompt (`agent/context.py`). No `logging` or `print` anywhere in `backend/app` (so no email or phone in logs; uvicorn access logs hold paths only).
- **Errors:** 500s carry no internals (no custom handler, so only "Internal Server Error"); provider errors return the exception class name only (`chat.py:88`, `loop.py:560-563`); 429 shows a wait message with retry (`planYear.ts:46-51`, `useAssistant.ts:101-104`); 410 on an expired family quietly starts a new one.
- **Wording:** urgent-care line is present on notifications and report next steps (`reports.py:35`, `notifications.py:41`), the reports prompt forbids delaying painful care (`loop.py:112-114`), and I found no text that tells anyone to delay care. The "book before Dec 31" notice is paired with the urgent-care line.
- **Deployment files read:** `backend/Dockerfile`, `render.yaml`, `netlify.toml`, `infra/aws/*` (service, nginx, user-data), `.env.example`. `ASSISTANT_ALLOW_ANONYMOUS` defaults to off, chat needs a token, `SESSION_SECRET` persists to `database/.session_secret`, CORS defaults to localhost only (the Netlify proxy makes the browser calls same-origin), `TRUST_PROXY` is documented (`docs/DEPLOYMENT.md:18`) but not set in `infra/aws/user-data.sh`: if the live host runs behind the proxy without it, every visitor shares one address and the 10-a-minute sandbox limit blocks the room after the 10th person.
